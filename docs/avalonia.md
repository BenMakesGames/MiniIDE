# Avalonia gotchas

- `TabControl.DataTemplates` (Control-inherited collection) selects the content template by the item's runtime type. Use it instead of `ContentTemplate` when items are heterogeneous (e.g. editor tab + image tab under one `TabControl`). Each `DataTemplate` needs an explicit `DataType`. `ItemTemplate` (tab header) can target the common base type because it only binds base members.
- `Avalonia.Data.Converters.ObjectConverters.IsNotNull` (and `IsNull`) are the idiomatic converters for gating `IsVisible` on a reference property being null/non-null. Wire with `Converter={x:Static ObjectConverters.IsNotNull}`. No custom `IValueConverter` needed.
- `Avalonia.Media.Imaging.Bitmap` ctor decodes synchronously and throws on failure. Wrap in `try/catch` when decoding user-supplied image paths; store the message for display.
- `IClassicDesktopStyleApplicationLifetime.Args` holds the launch arguments (nullable `string[]?`), already stripped of the exe path — `Args[0]` is the first real argument, do not skip it. Populated from the `args` passed to `StartWithClassicDesktopLifetime`. Guard for null before indexing/enumerating.
- A `ContextMenu` (and its `MenuItem`s) inherits the `DataContext` of the control it's attached to. On a control with no bound item — e.g. a top-bar `TextBlock` under the window — that resolves to the *window* `DataContext` (the VM), not a per-item model. Any `Click` handler reading `(sender as MenuItem)?.DataContext` must handle that VM type, or it silently no-ops. Shared path-resolver `switch`es should include a VM arm alongside the item-type arms.
- `ContextMenu.Opening` is a `System.ComponentModel.CancelEventHandler` (`(object? sender, CancelEventArgs e)`) — **synchronous**, so per-item enablement computed here cannot `await`; use only cheap cached state. Resolve the individual `MenuItem`s from `sender`: `((ContextMenu)sender).Items.OfType<MenuItem>()` matched on `mi.Name`. Named items **inside a `DataTemplate`** aren't in the window's namescope, so `this.FindControl<MenuItem>("...")` won't find them — resolve from the menu instead. It also runs *before the menu is parented* — see the next bullet for what that rules out.
- `ContextMenu.Opening` is raised **before the menu has a `DataContext`**. `ControlContextRequested` calls `CancelOpening()` (which raises `Opening`) and only then `Open()`, and `Open()` is where `_popup.SetPopupParent(control)` / `_popup.Child = this` happen — so on a menu instance's *first* open, the `ContextMenu` and its `MenuItem`s have no logical parent and nothing has propagated a `DataContext` into them. A handler that reads `cm.DataContext` (or a child `MenuItem`'s, or `PlacementTarget`) sees `null` and computes the wrong enablement, then looks correct on every later open because the popup stays parented while the attached control is in the visual tree — a bug that hides itself on the second right-click, and recurs per menu instance (so once per realized item in an `ItemTemplate`). Fix shape: **gate enablement with an `IsEnabled` binding per item** against the bound model (`IsEnabled="{Binding FilePath, Converter={x:Static ObjectConverters.IsNotNull}}"`), which is evaluated once the `DataContext` arrives inside `Open()`, before the popup shows. Reserve `Opening` for state reachable *without* the menu's `DataContext` — window-level VM fields, the focused editor — which is why menus computing from those are unaffected.
- To spawn a **visible** external terminal (vs. piping output), set `ProcessStartInfo.UseShellExecute = true` — the opposite of the output-capturing services (`RunService` uses `false`). `wt.exe` (Windows Terminal) is an app-execution alias that may be absent; a failed `Process.Start` throws `Win32Exception`. Attempt `wt.exe` (`ArgumentList` `-d <dir> <cmd>`), and on throw set an instance flag and fall through to `powershell.exe` (`WorkingDirectory = <dir>`, `ArgumentList` `-NoExit -Command <cmd>`). The flag makes subsequent invocations skip `wt.exe` for the app's lifetime. Only a *launch* failure of `wt.exe` should trip the fallback — a command failing inside a successfully-spawned terminal is not observable here and must not.
- To hand a path to **whatever program Windows registered for its extension** (the shell's default verb, i.e. what double-clicking in Explorer does), the path itself is the `FileName` — no program named — and you must also set **`ErrorDialog = true`**. It defaults to `false`, and .NET turns that default into `SEE_MASK_FLAG_NO_UI` on the `ShellExecuteEx` call (`if (startInfo.ErrorDialog) shellExecuteInfo.hwnd = startInfo.ErrorDialogParentHandle; else fMask |= SEE_MASK_FLAG_NO_UI;` — dotnet/runtime `Process.Win32.cs`), i.e. *the default tells the shell not to show UI*. With it suppressed, an extension whose association points at an uninstalled app throws `Win32Exception` with `NativeErrorCode == -2147221003` (`CO_E_APPNOTFOUND`, `0x800401F5`) and the action dead-ends; with it true the shell raises its own *"How do you want to open this file?"* picker and resolves the case itself. Set `ErrorDialogParentHandle` from `TopLevel.TryGetPlatformHandle()?.Handle` so the picker is owned by the window — it then centres on the window and draws in front of it. **The call blocks for the entire life of any dialog the shell raises** (measured: 206s with a picker left open), so never invoke it on the UI thread — `await Task.Run(...)` from the handler. Every way the user can dismiss that picker throws `Win32Exception` with `NativeErrorCode == 1223` (`ERROR_CANCELLED`) — Escape, *and* clicking the owner window, because the picker is a light-dismiss window that closes on focus loss rather than going behind. That is a user decision, so swallow 1223 rather than reporting a failure. Don't try to classify shell error codes and re-launch (`Verb = "openas"` is registered only on the `Unknown` ProgID, so it fails on any extension that *has* a ProgID) — let the shell own the decision tree. Shell-executing a **folder** just opens Explorer, so gate folders out of any such action or it duplicates "Open in Explorer".
- **Anything a `Task.Run` lambda captures must be resolved on the UI thread first.** Avalonia objects are thread-affine, and that includes the innocuous-looking accessors: a `Vm => (MainWindowViewModel)DataContext!` property reads an `AvaloniaProperty`, and `TryGetPlatformHandle()` reads the window. Writing `await Task.Run(() => Vm.Shell.DoThing(...))` therefore throws `InvalidOperationException: The calling thread cannot access this object because a different thread owns it` — *inside* the task, so it surfaces as the awaited call failing rather than as a threading error at the call site. Hoist the service and the handle into locals before `Task.Run` and let the lambda capture those.
- `MenuItem.InputGesture` is **display-only** — it renders the gesture text in the item's right-aligned column and registers *no* key handler. `MenuItem.HotKey` is what actually binds the key. Use `InputGesture` to advertise a shortcut that's already handled elsewhere (e.g. a global `KeyDown` handler) with zero double-fire risk. Accepts a `KeyGesture` string parsed at load (`"F12"`, `"Shift+F12"`, `"Ctrl+Shift+F"`), and coexists with a dynamically-set `Header` since it's a separate column.
- `DoubleTapped` only fires when **both** pointer presses resolve to the *same* source element ([Avalonia #8733](https://github.com/AvaloniaUI/Avalonia/issues/8733)). On templated item rows (e.g. `TreeViewItem`) where the content doesn't fill the container, the two clicks can straddle content vs. container padding → no `DoubleTapped`. Use a `PointerPressed` handler acting on `e.ClickCount == 2` instead — it fires wherever the press registers (everywhere selection already works). Register it **tunneling** (`AddHandler(PointerPressedEvent, h, RoutingStrategies.Tunnel)`) so it runs before the item consumes the press for selection, and do **not** set `e.Handled` (selection must still commit on that press). `ClickCount` is not source-sensitive — confirmed reliable across full row incl. edges/right-of-text.
- `TreeViewItem` has **no** `HorizontalContentAlignment`/`VerticalContentAlignment` (it derives from `HeaderedItemsControl`, not `ContentControl`) — a `Setter` for them fails to compile. Its Fluent template template-binds the header `ContentPresenter`'s `HorizontalAlignment`/`VerticalAlignment` to the *item's own* `HorizontalAlignment`/`VerticalAlignment`, and the default theme sets `VerticalAlignment="Center"` — so the presenter is shorter than the row, leaving top/bottom dead strips. To make row content fill the full height (uniform hit target), set `VerticalAlignment="Stretch"` on the item via a `TreeView.ItemContainerTheme` → `ControlTheme TargetType="TreeViewItem" BasedOn="{StaticResource {x:Type TreeViewItem}}"`. Horizontal is already `Stretch` and `Padding` already `0` in the Fluent theme. `BasedOn` the default (don't replace the template) or the chevron/indent/selection break.
- A `Button` can carry **both** `Command="{Binding …}"` and a code-behind `Click="…"` handler — both fire on a click, and **neither** fires while the button is disabled (`CanExecute` false). Use this to bolt a view-only side effect (e.g. surfacing a tab) onto a command-bound button without a `CanExecute` re-check in the handler and without pushing view state into the VM — the disabled state gates the click for free.
- Select a `TabItem` programmatically from code-behind by resolving both the `TabControl` and the target `TabItem` by `x:Name` (`this.FindControl<TabControl>("…")` / `FindControl<TabItem>("…")`) and setting `tabs.SelectedItem = tab`. Keep tab-activation a view concern here — don't model "selected tab" in the VM.
- **Heterogeneous `TreeView` nodes** (e.g. group headers vs. leaves): put a `TreeDataTemplate DataType="…" ItemsSource="{Binding Children}"` for parents **and** a plain `DataTemplate DataType="…"` for leaves in `TreeView.DataTemplates` (not `ItemTemplate`). Avalonia resolves per node by runtime type — same mechanism as `TabControl.DataTemplates`. A leaf `DataTemplate` with no children just renders a row.
- **Enumerating "the visible rows" of an un-virtualized `TreeView`**: `tv.GetVisualDescendants().OfType<TreeViewItem>().Where(i => i.IsEffectivelyVisible)` returns the flat, in-order list of rendered rows honoring collapsed subtrees — expansion state lives on the containers, not on the bound model. `IsEffectivelyVisible` is the right filter (walks up parent visibility). Requires `using Avalonia.VisualTree`. Not virtualization-safe: if virtualization is later turned on, off-screen containers won't be in the enumeration — audit callers.
- **`TreeView` tracks keyboard focus separately from selection.** Programmatically setting `tv.SelectedItem` only moves the blue selection highlight; the white keyboard-focus outline stays on the previously-focused container, and the built-in arrow-key handler navigates from *that* container next. Two visible cursors, and the next arrow key jumps from the wrong row. When a code-behind keyboard-nav path changes selection, also call `target.Focus(NavigationMethod.Directional)` on the target `TreeViewItem` — that syncs the focus outline and the arrow-key origin. Bundle both plus `BringIntoView()` into one helper so no future call site forgets a step.
- **`TreeViewItem.BringIntoView()` for keyboard-nav auto-scroll**: calling `BringIntoView()` on the target container scrolls it into the viewport. In this app it also piggybacks on the `TreeViewItem.RequestBringIntoView` class handler (`MainWindow` static ctor) that zeros the horizontal component — so the vertical scroll happens and the horizontal offset stays put. If that class handler is ever removed, every keyboard-selection path that calls `BringIntoView()` regains the horizontal-jitter regression.
- A control inside a **non-selected `TabItem`** (hand-authored `TabItem`, not `ItemsSource`) is not in the visual tree at window-ctor time, so `AddHandler(...)` in the ctor can miss it. Hook it via `AttachedToVisualTree="…"` on the control + a `bool` once-guard (mirrors the editor-binding pattern) — fires when the tab is first realized.
- **One realized control is shared across all same-`DataType` items in a `TabControl`.** When you switch between two tabs whose VMs resolve to the *same* `TabControl.DataTemplates` entry, Avalonia does **not** realize a fresh control per tab — it reuses the one control and swaps its `DataContext`. So any per-instance wiring done in code-behind (imperative `TextEditor.Document` assignment, event-handler subscriptions) must **rebind on every `DataContextChanged`**, not once on `AttachedToVisualTree`: keep a `Dictionary<Control, Binding>` of per-control state, guard with `ReferenceEquals(state.CurrentVm, newVm)` to skip redundant rebinds, and **detach the previous item's handlers** before wiring the new one — else handlers leak and stale documents keep firing. (A one-shot `HashSet<Control>` "already bound" guard is the trap: it binds the first item and silently no-ops for the rest.)
- **…and you must also unbind on `DetachedFromVisualTree`** — the other half of the above. Switching to a tab of a *different* `DataType` resolves a different template and therefore realizes a *different* control; the old one is discarded, but your dictionary still holds it, its document, its still-subscribed handlers, and any pending `CancellationTokenSource`. Nothing prunes that registry but you. **Teardown must be the exact inverse of setup**, including the one-time control setup (`LineTransformers.Add`, `AddHandler`, caret subscriptions) — otherwise a re-attach of the same control instance double-adds the transformer (double-colorized text) and double-fires the handlers. Corollary: **never subscribe with an anonymous lambda** in setup, or you cannot unsubscribe it; store the delegate. A clean shape is "setup returns its own teardown `Action`" so the two are written adjacently and can't drift (`Views/TabEditorBinder.cs`).
- **Don't search the visual tree for "the active X" — keep a per-kind binding registry and ask the one you want.** `descendants.OfType<TextEditor>().FirstOrDefault(e => e.DataContext == ActiveTab)` becomes ambiguous the moment a second tab kind (e.g. an output tab) also hosts a `TextEditor`. Constraining the predicate by VM type is a patch, not a fix. Because the two tab kinds resolve *different* templates, they own **disjoint control instances** — so one binder instance per kind means the code-editor registry structurally contains only code-tab editors, and the lookup is unambiguous by construction with no type guard at all. Merging the registries resurrects the ambiguity.
- **Binding an enum to `RadioButton`s** without a converter: expose one `bool` facade per value (`get => Enum == X; set { if (value) Enum = X; }`), bind each radio's `IsChecked` two-way to a facade, and in the enum's `partial void On…Changed` call `OnPropertyChanged` for every facade so the others uncheck. Clean for a 2–3 value toggle; reach for a converter only past that.
- A `[RelayCommand]`'s `CanExecute` that depends on **non-observable** service state (e.g. `SolutionService.SolutionPath`) won't re-evaluate when that state changes — expose a `NotifyCanRefreshChanged()` that calls `SomeCommand.NotifyCanExecuteChanged()` and have the owner invoke it after the state transition. `[NotifyCanExecuteChangedFor(nameof(SomeCommand))]` on an `[ObservableProperty]` covers the observable half automatically.
- A `MenuItem.Icon` whose `TextBlock` has an **explicit `Foreground`** keeps full color when the item is disabled — the hard-coded brush overrides the theme's disabled-foreground, so a greyed item shows a bright icon. Dim the whole item with a scoped `MenuItem:disabled → Opacity` style (put it in `ContextMenu.Styles`; `0.4` matches the `ComboBoxItem:disabled` precedent) — one item-level opacity dims icon + text together, no per-child binding. Same hazard bit the `ComboBoxItem` icon templates.
- Once **any** `MenuItem` in a menu carries an `Icon`, Avalonia reserves the icon gutter for **every** sibling — iconless items render blank-but-indented, aligned under the icons. Expected, not a regression.
- Icon glyphs on **static** `MenuItem`s (whose `DataContext` is the VM or a per-item model that doesn't carry the glyph) come via `{x:Static m:SomeIconClass.Xxx}`, not `{Binding}` — the static reference is `DataContext`-independent, so the same value works across menus attached to different sources. Needs the `xmlns:m="using:…Models"` declaration (already on the window root here).
- **Clicking the already-selected `TabItem` raises no `SelectionChanged`.** Any "reveal the panel when a tab is clicked" behavior built on `SelectionChanged` silently misses the case where the clicked tab is already active. Hang it off a **tunneling `PointerPressed`** on the `TabControl` instead (`AddHandler(PointerPressedEvent, h, RoutingStrategies.Tunnel)`), and do **not** set `e.Handled` — the press still has to commit the selection. Same shape as the `TreeView` double-click handlers.
- **The middle mouse button has no click event** — no `Tapped`, no `Click`, no `MiddleTapped`. It surfaces only as `e.GetCurrentPoint(visual).Properties.PointerUpdateKind == PointerUpdateKind.MiddleButtonPressed` inside a `PointerPressed` handler. That makes middle-click-to-close (`MainWindow.axaml.cs` `OnTabHeaderPointerPressed`) the one pointer handler here that is **bubbling and sets `e.Handled`** — the inverse of the tunneling handlers above, which exist precisely so they *don't* handle the press. The rule that keeps both shapes safe: handle the press only inside the middle-button branch and `return` before it otherwise, so left-click selection and the right-click `ContextMenu` are untouched. Wiring it as `PointerPressed="…"` on the `ItemTemplate`'s root panel (rather than on the `TabControl`) means the item is already the `DataContext` — no hit-testing needed.
- **`SelectionChanged` bubbles, so a handler on a `TabControl` also fires for every `ListBox`/`TreeView` *inside* its tabs.** A "start work when my tab is selected" hook wired to `BottomTabs.SelectionChanged` will be tripped by picking a list item three tabs away. Guard on `ReferenceEquals(e.Source, TheTabControl)`. Distinct from the tunneling `PointerPressed` above: that one is expand-on-click, this one is selection — a control can need both, and conflating them gets you neither.
- `{Binding !SomeBool}` negates inline — a two-state indicator is two elements with `IsVisible="{Binding X}"` / `IsVisible="{Binding !X}"`, not a converter.
- **`DispatcherTimer(TimeSpan, DispatcherPriority, EventHandler)` starts the timer.** If the point is to poll only while something is shown, that ctor is already polling. Use `new DispatcherTimer { Interval = … }` + `Tick +=`, then `Start()` where you mean it.
- **`TabControl` has no header-area extension point.** To float a button over the tab strip, wrap the `TabControl` in a single-cell `Grid` and make the button a *sibling* (second child, `HorizontalAlignment="Right"`), not a child. Keeping it outside the `TabControl`'s visual tree is what stops a tunneling `PointerPressed` handler on the `TabControl` from also seeing the button's own press. Forking the `ControlTemplate` for a real slot is disproportionate.
- **A `TabItem`'s `Bounds` keeps reporting its *unclipped* height when the `TabControl` is squeezed below it** (Fluent's `TabItem` MinHeight is 48). So `Height="{Binding #SomeTab.Bounds.Height}"` is a trap for "make this element as tall as the header strip": it's right at full size and wrong the moment the strip is clipped — the element stays 48 tall inside a 22px bar and its centered content lands past the bottom edge. Drive such a height explicitly from the code that owns the layout state instead.
- **`RowDefinition.MinHeight` is honored by `GridSplitter`** — the idiomatic way to stop a drag stranding a panel at an unusable height (no code needed). But a *programmatic* collapse below that floor must zero `MinHeight` **before** assigning the smaller `Height`, or the floor clamps the row straight back up and the collapse silently no-ops. Restore both together. Note `RowDefinitions="*,4,220"` shorthand can't express `MinHeight` — expand to explicit `<RowDefinition>` elements.
- To make a `GridSplitter` non-draggable, set `IsEnabled = false`. An explicit `Background` on it survives the disabled state (same override-the-theme mechanism as the `MenuItem.Icon` `Foreground` case), so the seam keeps its color and just stops responding.
- Don't `await` startup work inside `OnFrameworkInitializationCompleted` — it runs before the window is shown and stalls startup. Construct the VM into a local, bind it to the window, then `Dispatcher.UIThread.Post(async () => await vm.SomeCommand.ExecuteAsync(...))` to defer the work until after the window is up. Reuse the same VM instance the window is bound to — don't construct a second one.
- **Child processes started with `UseShellExecute = false` / `CreateNoWindow` are not reaped when the app exits** — Windows has no parent-child job link by default, so every still-running `Process.Start` child outlives the window as an orphan. If the app can have N of them live at once (e.g. one per run tab), shutdown cleanup is mandatory, not a nicety: kill them from the window's `Closed` handler. Keep the walk in the VM (`vm.StopAllRuns()`) and the handler thin, the same way `Watcher.Dispose()` is reached there. `Kill(entireProcessTree: true)` is the right call when the child is itself a launcher (`dotnet run` spawns the app as *its* child — killing only `dotnet` leaves the app alive).
- **`[RelayCommand(CanExecute = nameof(X))]` accepts a `bool` *property*, not just a method.** Point it at an `[ObservableProperty] bool` and add `[NotifyCanExecuteChangedFor(nameof(TheCommand))]` to that field: the button's enabled state then tracks the flag with no manual `NotifyCanExecuteChanged()` anywhere. (The method form is still needed when the gate reads non-observable service state — see the `NotifyCanRefreshChanged` bullet above.)
- **Adding chrome (a toolbar strip, a status line) inside a `DataTemplate` inherits the one-realized-control rule** — the strip is realized once and reused as the `DataContext` swaps between items, exactly like the editor beside it. So everything it shows must come from the bound item, never from control-local state, and "this item doesn't get the strip" is an `IsVisible` binding to a per-item flag — not a second template, and not code-behind that hides it. Corollary for a flag like "a run is attached here": make it *sticky* per item rather than recomputing from live state, or the strip appears and disappears mid-item and reflows the content below it.
- **`FlyoutBase` is an `AvaloniaObject`, not a `StyledElement`** — it has no `DataContext` and is not in any tree. Bindings on a flyout's *own* properties (`MenuFlyout.ItemsSource`) still work because `PopupFlyoutBase.ShowAtCore` calls `Popup.SetPopupParent(placementTarget)`, which parents the popup (and so the presenter and its content) to the control the flyout hangs off. Content inside `<Button.Flyout><Flyout>…` therefore inherits the target's `DataContext` and resolves `{StaticResource}` normally.
- **`MenuFlyout.ItemContainerTheme` setter bindings resolve against the *parent* VM, not the item** ([Avalonia #18146](https://github.com/AvaloniaUI/Avalonia/issues/18146), open). That's the only hook for per-item `MenuItem.ToggleType` / `IsChecked` / `Command`, so a data-bound radio/check menu built on `MenuFlyout` + `ItemsSource` does not work. Options: put `MenuItem`/`Separator` *instances* in the collection (`MenuBase.NeedsContainerOverride` returns false for those two types, so each is used as its own container — but that means controls in a VM), or drop to a plain `Flyout` with hand-laid content, where ordinary compiled bindings apply.
- **`MenuFlyout.Items` and `MenuFlyout.ItemsSource` are mutually exclusive** — `ItemsSource` calls `Items.SetItemsSource(…)`, which throws if inline children exist. So a flyout cannot mix static rows (group headers, separators) with a bound list; either everything comes from the collection, or each dynamic group is a submenu `MenuItem` with its own `ItemsSource`.
- **`SplitButton` disables *both* halves when its `Command.CanExecute` is false** (`IsEnabledCore => base.IsEnabledCore && _commandCanExecute`). So a flyout that configures the command's own inputs becomes unreachable exactly when the command is unavailable — fine when the flyout only tunes an action, worth knowing before putting unrelated settings in one.
- **Data-bound radio rows**: bind `RadioButton.IsChecked` **one-way** to a per-item `IsSelected` and put the write on `Command`/`CommandParameter`. The click's own toggle is a `SetCurrentValue` that leaves the binding intact, so the VM's answer lands right after and self-heals if the two disagree. Two-way `IsChecked` instead means every group member writes back (including the automatic un-checks) and the VM has to sort out which write was the user's.
- **A plain `Flyout` does not light-dismiss when its content is clicked** (unlike a `MenuFlyout`, where picking an item closes the menu). That is a feature for a popup holding several independent settings and a bug for one that acts like a menu — pick the flyout type by which behavior you want.
- **Verifying focus-time behavior (`Window.Activated`) from a script: `SetForegroundWindow` is not enough.** Windows' foreground lock silently ignores the call from a non-foreground process, so a scripted "focus another window, then focus back" often produces *no* deactivate/activate cycle and the `Activated` handler never runs — which reads as a broken feature when the wiring is fine. `ShowWindow(hwnd, SW_MINIMIZE)` followed by `SW_RESTORE` forces a real cycle every time. Applies to anything hung off `Activated` (here: the disk-refresh safety net and the git repo-state poll).
